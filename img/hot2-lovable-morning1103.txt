<p>German security firm Crissy Field scanned 159,041 projects built with the AI app maker Lovable, found in public web archive data from December 2025 to September 2026, and found records containing email addresses readable without a login on 7,403 of the sites it examined closely. Among the worst cases were more than 1,000 identity document records with passport numbers, more than 80,000 forum profiles, more than 200,000 chat messages, and ticket and food sale records carrying payment information. The researchers could not establish whether any of the data was misused, and they describe no break-in at Lovable itself: the cause, they say, is access-control misconfiguration in the apps' databases, not a hack.</p>

<h2>The funnel, in numbers</h2>
<p>The headline figure, 7,403 sites, is easy to misread, so the full funnel matters. Crissy Field started from 159,041 Lovable projects found in Common Crawl data. Of those, 34,545 used Supabase, the hosted database service many Lovable apps use. On 24,664 of the Supabase apps, the page sent database records as soon as it loaded, which is not a problem by itself if the data is meant to be public. With further read-only requests using the same key the page itself used, the researchers found records containing email addresses in 10,560 tables across 7,403 sites. The table below adds ByteHerald's own percentages, computed from the researchers' counts and labeled as such, so readers can see each step's size instead of only the final number.</p>

<p>Two cautions travel with these numbers, and both come from the researchers themselves. First, the 30 percent figure is not a confirmed leak rate: some email addresses could be public contact addresses or test entries, records without an email address were not counted, and the sample covers only Lovable apps using Supabase, not Lovable's newer database feature. Second, the researchers downloaded only parts of the datasets they found, so the real counts of exposed records may be higher than the examples given. A reader who quotes 7,403 without those two cautions is overstating what the study proves, and a reader who dismisses it because 4.7 percent sounds small is understating it, because the exposed records include passports and payment information, where a single table is enough.</p>
<h2>Why a public key is not a lock</h2>
<p>The mechanism is the oldest mistake on the web, now generated at a speed no security team has had to handle before. A Lovable app usually talks to its Supabase database straight from the browser, using a public key that is built into the page on purpose. That design is safe only if every table has Row Level Security switched on, with a policy that says who may read which rows. Supabase's own guide is blunt: enable Row Level Security on every table in an exposed schema. When a table has no such policy, or a policy that lets everyone in, anyone who loads the page can ask the database for rows that were never meant to be public, using the same key the app itself uses. No password guessing, no exploit, and no breach of Lovable's own systems is needed.</p>
<p>This is the third public warning about the same pattern, not the first. In March 2025, researcher Matt Palmer disclosed that 170 of 1,645 Lovable apps he scanned had database locks that let anyone read or change their data, a finding recorded as CVE-2025-48757. In September 2026, security firm UpGuard reported 16,326 Supabase databases with tables anyone on the internet could read, across roughly 300,000 domains showing signs of Supabase use, and noted that Supabase had changed its Table Editor so tables made there have Row Level Security switched on by default, while that safeguard does not cover tables created through the programming interface, which is the route AI coding agents use. Crissy Field's November 2026 scan is larger than both earlier studies and specific to Lovable, and it shows the same root cause surviving two rounds of warnings.</p>
<h2>Who is responsible, and the check that catches it</h2>
<p>Responsibility is the contested part of this story, and the reporting is clear about where each party stands. Lovable told Handelsblatt, the German business paper that reported the findings on November 2, 2026, that the problem is common across the industry, and under Lovable's terms the customer is responsible for the app and how it handles data, according to Crissy Field and coverage of the report. Lovable's security documentation describes scans that run before publishing and on demand, which check database access rules, and reporting on the platform notes that its automatic Quick scan covers tables with no lock at all, while its deeper Deep scan, which checks whether users can view data that is not theirs, must be started manually. Supabase, for its part, has said its projects are secure by default while customers control how their own projects are configured. None of that changes the practical test for any app owner, and the test costs nothing: open your live app signed out, try to read another user's record, and for each table, explain in plain words who can read and change its rows. If that explanation cannot be written, the table is not ready for real customer data, whatever the scan said.</p>
<p>For readers who want the wider pattern, ByteHerald's <a href="https://www.byteherald.com/2026/10/assume-breach-2026-ai-security-report.html">Assume Breach security report card</a> catalogued nine 2026 AI security incidents with grades by category; the Lovable exposure belongs in the same data-exposure class, with the same lesson the report card drew, that the failure is usually configuration, not cryptography. The Crissy Field report does not name the affected apps, and it does not publish how it reached the data, so this article names no app and gives no retrieval method. What it does give is the funnel, the mechanism, and the one check that would have caught it, because those are the parts an app owner can act on today, before the next scan finds their table in it.</p>
