<p>ByteHerald's reconstruction of Anthropic's own status records shows that November 13, 2026 was not one outage but two different failures with a 71 minute gap between them. The first failure locked users out at sign-in for exactly 120 minutes and left the Claude API off the affected list. The second lasted 149 minutes, reached the API, and widened during the afternoon to connectors, Managed Agents and Claude Security. Anthropic published no root cause for either incident.</p>
<p>That split matters because the two incidents broke different promises. A sign-in failure stops people reaching the product while applications built on the API can keep running. An API failure reaches those applications as well. Treating the day as a single outage hides which customers were exposed and for how long.</p>

<h2>What the records do not establish</h2>
<p>Analysis: the status records establish timing and scope, not cause. They do not state what broke authentication in the morning, why errors returned in the afternoon, how many users were affected, or whether the two incidents shared a cause. The Microsoft 365 connector problem was tracked separately from November 12 and attributed by Anthropic to a Microsoft 365 service incident, so it should not be folded into either Claude incident total.</p>
<p>The practical reading is narrow. On November 13, sign-in dependent surfaces carried 120 minutes of documented incident time, API dependent work carried 149 minutes, and the overlap between the two windows was zero. Any reliability claim for that day should state which surface it describes.</p>
<p>The component lists carry a second lesson for anyone running Claude in production. During the morning incident, the documented scope stayed on sign-in dependent surfaces, so an integration calling the API directly faced a different risk from a team using Claude Code interactively. During the afternoon incident that separation collapsed, because the API itself entered the affected list and connectors degraded afterward. A fallback plan built only for chat outages would have covered the morning and missed the afternoon.</p>
<p>Our duration method also has a stated limit. A status post timestamp marks when Anthropic published an update, which can lag the moment errors began or ended for individual users. The ledger therefore compares documented windows consistently across incidents. It should not be read as a per-user downtime measurement, and it does not estimate lost work, failed requests, or revenue impact, none of which the status records quantify.</p>
