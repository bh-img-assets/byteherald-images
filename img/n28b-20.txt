<p>ByteHerald's recomputation of Cerebras's Kimi K3 example shows why the wafer count is 59 and why it should not be read as a benchmark. At 4 bits per parameter, a 3 trillion parameter model carries about 1.5 terabytes of weights. Spread across 93 layers, that is about 16 GB per layer. A 44 GB wafer can hold two linear-attention layers, but a dense layer gets a wafer to itself so the remaining space can hold key-value cache. The result is 35 wafers for 69 linear layers plus 24 wafers for 24 dense layers.</p>

<h2>Why memory placement drives the design</h2>
<p>Cerebras said weights stay on the wafer where their layer runs and only activations move between wafers, at roughly 2 microseconds per hop over RDMA on Ethernet. That matters because moving weights for every token would waste the advantage of on-chip memory. The pipeline also keeps different requests in different stages at the same time, and micro-batches let a stage process small groups rather than one request at a time.</p>
<p>Analysis: the scarce resource is not arithmetic alone. Dense layers need cache space that grows with context and concurrent requests, while linear layers keep a fixed-size state. That difference explains the uneven packing rule. It also explains why a simple division of total weights by 44 GB understates the system size. The correct constraint is layer type plus cache headroom, not total bytes alone.</p>
<h2>What the example does not prove</h2>
<p>Cerebras calls Kimi K3 an illustrative example and states a target of 1,000 to 2,000 plus tokens per second for multi-trillion parameter models. The post does not publish a measured Kimi K3 run with request mix, output length, power draw or cost. Cerebras itself says the more meaningful efficiency metric is token throughput per unit of power at the same output speed. Without that measurement, 59 wafers is a capacity statement, not evidence of lower cost per token.</p>
<p>Analysis: the durable finding is the packing rule. If a future model has more dense layers or longer average requests, wafer count rises for cache reasons even when weight bytes stay similar. Buyers should ask for measured throughput per megawatt and concurrent-request limits at the stated context size before treating the example as a deployment claim.</p>
<p>Analysis: the example also shows why wafer count alone is a weak comparison metric. Two systems can hold the same model and differ in concurrent requests, output speed, power draw and failure behavior. Cerebras states that production stages are finer-grained than the one-layer illustration and that micro-batch size trades per-request speed against total throughput. A buyer comparing wafer-scale inference with GPU inference should therefore fix the workload first: prompt length, output length, concurrency, latency target and quality settings. Only then do tokens per second and tokens per megawatt become comparable. The 59-wafer figure answers the capacity question. It does not answer the procurement question.</p><p>The ledger should be updated if Cerebras publishes measured Kimi K3 serving data.
