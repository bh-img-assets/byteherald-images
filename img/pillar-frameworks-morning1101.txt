<p>One developer built the same small Pokemon app 12 times, once in each of 12 JavaScript frameworks, using the same coding agent, and the bill changed by almost two times from cheapest to priciest. The cheapest build, Hono plus htmx, cost 2.67 dollars per run in the benchmark's accounting. The priciest, Angular, cost 4.97 dollars. That 2.30 dollar gap is the headline, but it is not the whole story: the priciest framework also took more than twice as long, used more than twice as many tokens, and produced almost half again as much code to maintain.</p>

<h2>How the benchmark was run</h2>
<p>The benchmark comes from <a href="https://nolanlawson.com/2026/10/28/the-ai-cost-of-javascript-frameworks/">Nolan Lawson, published on October 28, 2026</a>, and it was designed to answer a question the web community usually answers with vibes: which framework is actually cheaper when an agent, not a human, does the typing. Lawson gave Opus 5.5, at high effort, a specification for a small but non trivial Pokemon app using PokeAPI, with search, filtering, and pages for types, moves, and game data. Each framework was told to use its official MCP or skills where one existed. Each agent ran in a sandbox, without knowledge that its output would be tested in Lighthouse, although it was given the conformance test suite. The app was tested against that suite, based on the accessibility tree rather than the raw DOM, so no framework was forced into a particular HTML structure.</p>
<p>Each framework was built 3 to 5 times and the median was reported, which matters because agent runs are stochastic. Angular is the exception: it failed to create a working app twice, so its median comes from 3 iterations, not 5. Lawson also did not mandate a CSS methodology, apart from avoiding Tailwind, Bootstrap, or any other component framework, and did not specify server side rendering versus client side rendering, or that the app should be as performant as possible. The point was to simulate what a typical agent led build does, not what an expert optimizing for a benchmark would do.</p>
<p>Two caveats from Lawson himself should travel with every number below. First, the app is one holotype: a relatively content based site with little interactivity, closer to Wikipedia than to Figma or Gmail, so a complex dashboard, a video game, or a productivity app could rank frameworks differently. Second, Lighthouse and Core Web Vitals are biased against single page apps, so multi page frameworks are almost guaranteed to win on metrics like Total Blocking Time and JavaScript bytes. The benchmark is still useful, because it measures what it measures honestly, and because it replaces a slogan with a table.</p>

<h2>Why the expensive frameworks cost more</h2>
<p>Lawson gives a different explanation for each of the three priciest frameworks, and the explanations are more useful than the ranking. For SvelteKit, agents read the SvelteKit version 3 migration guide in every run, likely because version 3 was too new to be in Opus 5.5's training data. For Gracile plus Lit, agents did not know the framework well and either cloned the Gracile repository or read its compiled source from node modules. For Angular, the cost seems to follow total code size, which leads to the second table below.</p>
<p>The tooling story is messier than a vendor pitch would suggest. Not every agent used the MCP or skill that was installed. TanStack Start's agent only discovered its skill files in 2 of 5 runs, because they shipped inside node modules. Nuxt's MCP was never used by the agents. Next.js agents read the skill file in only 1 of 5 runs and the AGENTS.md file in 2 of 5 runs. Lawson's conclusion is blunt and worth repeating: he doubts many agent led builders are shouting at their agents in all caps to use the MCP, and plenty are probably skipping it entirely. A framework whose official tooling the agent never finds is, in practice, a framework without tooling.</p>

<p>Read the two tables together and a pattern emerges that neither table shows alone. Hono plus htmx is cheapest to build, smallest to maintain at 1,370 lines, and light to ship at 18 KiB, which is why Lawson notes it does roughly the same thing as Angular with about 70 percent of the code, and faster. Astro is the fastest to build, the lightest to ship at 0 KiB of JavaScript in the median run, and the fastest to paint at 810 ms, which is what a multi page framework should do on a content site. Angular is the outlier in the other direction: most lines at 2,009, highest blocking time at 103 ms, and the only framework that failed twice, when its agent built a server side app that rejected non localhost requests even though the instructions said the app would sit behind a reverse proxy.</p>
<p>Vanilla JavaScript is the surprise that keeps the benchmark honest. With no UI framework at all, just Vite, it underperforms several frameworks on cost and tokens, which suggests having some framework can be better than nothing, or at least better than raw Vite. Lawson also notes that the Vanilla agent still chose to build a single page app in all 5 runs, and that Gracile's agent did not even use Lit in 2 runs. The benchmark measures what agents actually do with a framework, not what the framework's documentation says they should do.</p>
<h2>How to choose, by what you actually care about</h2>
<p>A single winner would be a lie, because the tables disagree depending on the question. If the question is build cost alone, Hono plus htmx wins, with Astro and Nuxt close behind. If the question is token efficiency alone, Nuxt wins at 3.85 million tokens, ahead of Astro at 4.13 million. If the question is shipped weight alone, Astro wins at 0 KiB, ahead of Vanilla at 7 KiB and Gracile plus Lit at 8 KiB. If the question is maintenance alone, Hono plus htmx wins again at 1,370 lines. Next.js is the cautionary case: a middling build cost at 3.14 dollars, but the heaviest shipped JavaScript at 142 KiB and the slowest paint at 2,090 ms, with part of that variance explained by one app avoiding lazy loading images while four did not.</p>
<p>That disagreement is the benchmark's real contribution. In the human typing era, framework choice was largely about developer experience: how it felt to type JSX, or whether the virtual DOM was fast. In the agent era, the developer is less constrained by typing, and the costs that matter shift to tokens per build, lines per future edit, and bytes per user. A framework that is pleasant to type in can still be expensive to build with, and a framework that is cheap to build with can still ship a heavy page. The honest decision table is the two tables above, read against the kind of app you are actually building.</p>
<p>For a content heavy site like the benchmark app, the evidence points to a multi page approach: Astro, Hono plus htmx, or Nuxt, with the choice between them turning on whether you value shipped weight, token efficiency, or the smallest codebase. For a highly interactive app, this benchmark does not settle the question, and Lawson says so himself: a dashboard, a video game, or a productivity app could favor a single page framework, and in app interactivity metrics would be a fairer test than Lighthouse alone. Anyone who cites this benchmark to claim a framework is best for every app is misusing it.</p>
<p>Framework choice is only one half of the agent coding bill. <a href="https://www.byteherald.com/2026/10/5-ai-coding-assistants-one-scorecard.html">ByteHerald's earlier scorecard compared five coding assistants on the same tasks, and the assistant you choose changes the output before the framework ever gets a say</a>. The other half is price, and it moves fast: <a href="https://www.byteherald.com/2026/10/gpt-6-vs-claude-vs-gemini-october-2026.html">our October price tracker recorded 10 models and a price war timeline, so a framework ranking measured at one model's prices will drift as those prices change</a>. Lawson's benchmark is a dated snapshot, October 28, 2026, Opus 5.5, specific framework versions listed in his addendum, and it should be re run, not quoted forever.</p>
<h2>What would make the next benchmark better</h2>
<p>Lawson lists the improvements himself, and they are a good checklist for anyone who wants to challenge his ranking. Run more iterations, use different coding agents, try different effort levels, use different framework versions, test with and without MCPs and skills, test in more browsers than Chromium, build different kinds of apps, and mandate or forbid specific performance techniques such as service workers, image optimization, lazy loading, fetchpriority, and the Speculation Rules API. He also notes a cheating vector he deliberately closed: pre generating all HTML files as static assets, which he forbade in the instructions and checked in the test harness, because the aim was to simulate a large volume of possibly dynamic data.</p>
<p>The benchmark code is on GitHub, and Lawson invites forks and corrections. That openness is what makes the tables citable rather than merely quotable: another team can re run the same spec, change one variable, and show where Lawson's ranking holds and where it breaks. Until that happens, the defensible claim is narrow and strong. On one content app, with one agent, in October 2026, the cheapest framework cost 2.67 dollars per run and the priciest cost 4.97 dollars, and the gap was not random: it tracked code size, training data freshness, and whether the agent ever found the framework's own tooling. If you are re evaluating how you build software in the agent era, as Lawson suggests, re evaluate what you type after npm install, and do it with a table, not a slogan.</p>
