<p>A tampered version of the Claude Code extension for VS Code, version 2.1.313, was distributed through the Cursor marketplace for about 11 hours on October 29, 2026, and planted a persistent SSH backdoor on developer machines. Cursor said at most 5,000 users were affected. Anthropic said it did not build or publish the tampered version. The incident matters because the package carried the legitimate extension identity, so checking the publisher name alone would not have caught it.</p>

<h2>What happened, in one paragraph</h2>
<p>Researchers at <a href="https://phorion.io/blog/offical-claude-code-vsx-compromise/">Phorion</a> spotted the backdoor in the official Claude Code for VS Code extension bundle on the Cursor marketplace. Cursor said the malicious version was available from about 2:27 a.m. to 1:35 p.m. Pacific Time on October 29, 2026, and that it removed the version immediately on detection, then shut its whole VS Code marketplace down as a precaution, audited other extensions, rotated its keys, and rebuilt the marketplace before bringing it back. The company also worked with the hosting provider to take the attacker server offline, which stopped the reverse tunnel and the beacon traffic from working. Anthropic published version 2.1.314 to Open VSX and the Microsoft VS Code marketplace, and Cursor asked customers to update to 2.1.314.</p>
<p>The one question nobody has answered yet is how the tampered package got published under the legitimate extension identity in the first place. Anthropic said, <a href="https://www.theregister.com/cyber-crime/2026/10/30/anthropic-that-claude-code-extension-compromise-couldnt-be-us/5306682">via The Register</a>, that a malicious actor used access to the Cursor marketplace to publish a tampered copy that Anthropic did not build or publish, and that its own systems and employee laptops were not compromised. Cursor has not explained the publishing mechanism, and has said it found no evidence that any other extension version or the official distribution was affected. Until that mechanism is explained, this story is not closed, even though the malicious version itself is gone from the store.</p>
<h2>How the backdoor worked</h2>
<p><a href="https://phorion.io/blog/offical-claude-code-vsx-compromise/">Phorion's analysis</a>, which is the most detailed public account, describes a malicious loader inserted at the start of the extension's main JavaScript file, before the legitimate code. The rest of the bundle looked like the standard extension, with normal activate and deactivate exports. The loader pulled in standard Node.js modules and ran as soon as Node loaded the file, before the extension's normal activation code. A developer did not need to click anything in Claude Code for the payload to fire. Simply loading the extension was enough.</p>
<div class="separator" style="clear: both; text-align: center;"><img src="https://raw.githubusercontent.com/bh-img-assets/byteherald-images/main/img/hot1-cursor-midday1030-chart.png" alt="Diagram: five stages of the backdoor, from load to plant key to open tunnel to stay to report" /></div>
<p>From there the payload followed four steps. First, it created the user's .ssh folder if needed and appended an attacker-controlled Ed25519 public key, labelled svc-telemetry, to the authorized_keys file, so the attacker could log in as that user if SSH was running. Second, it tried to make sure SSH was running and to open a reverse tunnel to the attacker server at 134.209.82.225, which would let the operator connect back into the machine through that tunnel. Third, it installed persistence so the tunnel would come back after a reboot. Fourth, it sent a one-off beacon with host details back to the attacker server.</p>

<h2>The bug that limited the damage, and why it is not a defence</h2>
<p>On macOS, the payload tried to check whether Remote Login was off by running systemsetup without administrator rights. As a standard user, that tool prints an administrator-access error and exits with status 0, instead of returning Off. Because the script only tried to turn SSH on when the output contained Off, it skipped the enablement step entirely on those machines. If SSH was not already running, the tunnel could still connect out, but traffic forwarded back through it would hit a closed port 22 on the local machine. Phorion and Cursor both reached the same conclusion: the bug reduced the impact on many Macs, but it did not make those machines safe.</p>
<p>Three facts keep this from being a reassuring story. The key and the persistence still landed on those machines. If the user already had Remote Login enabled, or turns it on later, the backdoor is ready to use. And the beacon still went out, giving the operator a list of hosts and the names of credential variables on each one. The Windows path had its own bug, passing a service setup command through a helper that hardcodes a Unix shell path, and the Linux path had a cron check that could wipe existing user cron jobs on repeat runs. Buggy malware is still malware, and its bugs cut both ways: they limited some access paths while creating new cleanup hazards.</p>
<h2>What was taken, and what was not</h2>
<p>The beacon collected hostname, username, operating system and architecture, home and working directories, the global Git email address, the public IP address, and the status of each setup stage. It also collected the names, not the values, of up to 40 environment variables matching key, token, secret, password, AWS, or GCP patterns. That distinction matters. The beacon did not exfiltrate secret values themselves, but it told the operator exactly which machines were worth prioritising for a follow-up attempt. Phorion is explicit on this point, and it is the reason Cursor's advice goes beyond updating the extension.</p>
<p>The payload contained no privilege escalation exploit. Its attempts to start system services used non-interactive sudo, which fails unless passwordless sudo is already configured, and its Windows scheduled task required administrator rights, falling back to a per-user Startup folder entry when that failed. That is why the practical risk varied so much by machine: a developer machine with SSH already enabled and a permissive sudo setup was in a very different position from a locked-down laptop where every service step failed. Both machines still needed the same cleanup check, because the key and persistence steps did not depend on those service steps succeeding.</p>
<h2>What to do if you installed 2.1.313</h2>
<p>Cursor's advice, echoed by Phorion, is to treat any machine that installed or updated to 2.1.313 from the Cursor marketplace in the exposure window as affected until proven otherwise. Updating to 2.1.314 is necessary but not sufficient, because the payload drops standalone scripts that keep running after the extension is gone. The cleanup sequence below follows Cursor and Phorion, in the order they give it.</p>

<p>One scope correction matters for anyone who saw early reports. Initial reports suggested that npm, Open VSX, and the Microsoft VS Code marketplace were also affected. Later reporting confirmed that Cursor was the only source distributing the malicious extension, and that the official channels were not affected. If you installed Claude Code from Microsoft's marketplace or Open VSX, this incident does not apply to that install. If you installed it through Cursor in the window, the cleanup check applies even if nothing looks wrong.</p>
<h2>Why extensions are a supply chain, not just a download</h2>
<p>An editor extension runs with the permissions of the IDE and the user running it, which means a backdoored extension gets immediate access to local files, source code, and developer tooling as soon as its module loads. That is the evergreen point of this story, and it survives after this specific version is forgotten. A marketplace is not a neutral shelf. It is a trust boundary, and this incident shows what happens when a package passes that boundary under a legitimate identity: every downstream check that trusts the publisher name inherits the failure.</p>
<p>That is why ByteHerald's earlier security reporting argued for assuming breach and verifying, rather than trusting a clean-looking install. Readers who want that longer argument should read our <a href="https://www.byteherald.com/2026/10/assume-breach-2026-ai-security-report.html">assume-breach security report</a>, which sets out why a single trusted component cannot carry the whole security case. The practical version of that argument for extensions is short: pin versions where you can, monitor authorized_keys and persistence locations as a routine check rather than only after an incident, keep SSH off on machines that do not need it, and treat any extension update that arrives outside your normal update path as a reason to pause. None of those steps would have stopped a legitimate-identity package from installing, and that honesty is the point. The steps that matter here are the ones that limit what a bad install can do next, and that make its traces visible.</p>
<h2>What to watch next</h2>
<p>Three things will decide whether this incident stays contained. The first is Cursor's explanation of the publishing mechanism, which is still missing. The second is whether Cursor's direct outreach reaches all affected users, since the company said it plans to contact them directly and the at-most-5,000 figure is its own upper bound, not an independently audited count. The third is whether any affected machine shows evidence of an inbound login, which would change the story from attempted access to successful access. ByteHerald will update this article if Cursor publishes that explanation or if any of those three points changes, rather than publishing a competing post.</p>
