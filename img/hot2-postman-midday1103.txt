<p>On October 25, 2026, a Postman user reported that simply opening Postman desktop auto-installed plugins into Codex and Claude Code and tried to trust its own startup hook, without asking. The report documents a consent failure, not a proven data theft: the remote connection it created never authenticated, so no data flowed through it in this case. That distinction is the whole story, because the violation is real even though the worst fear is not proven.</p>

<h2>What the logs show</h2>
<p>The report, filed as issue 14370 in Postman's public support tracker on October 25, 2026, is a forensic account from one Mac, not a press release. The user opened Postman desktop version 12.33.4 and then found recurring authentication warnings and Codex routing API work through Postman skills. Investigation of Postman's own log showed an entry timestamped October 24, 2026, at 09:34 UTC, recording an automatic installation with the source label "auto-existing-upgrade" and the results "claude-code:installed" and "codex:installed". The changes found on the machine were:</p>
<table>
<tr><th>Change</th><th>What was found</th></tr>
<tr><td>Codex plugin</td><td>Postman plugin version 1.1.0 installed, with Codex's global configuration changed to load it from Postman's plugin repository, plus a trusted hash for the plugin source</td></tr>
<tr><td>Claude Code plugin</td><td>Postman plugin version 2.0.1 recorded in Claude Code's installed plugins at user scope, with the same October 24 installation timestamp</td></tr>
<tr><td>Startup instruction hook</td><td>An attempt to approve Postman's own instruction hook in the coding agent's configuration, the step the reporter calls a trust-boundary problem</td></tr>
<tr><td>Remote MCP connection</td><td>A connection pointing at Postman's remote MCP server, enabled but never working, because Codex logs show startup failed with authentication required</td></tr>
<tr><td>Postman CLI</td><td>A Postman executable and its library directory present in the user's local binary folder, with modification times matching the installation window</td></tr>
</table>
<p>Each of these is the kind of change that should require a clear, specific opt-in in the affected application. Installing a plugin, adding a remote connection, and trusting a hook in another program are three separate permissions, and the report shows all three happening as a side effect of opening a different application. The reporter states the principle plainly: an API client should not make itself the default workflow in other tools simply because the user opened it.</p>

<h2>What it does not prove</h2>
<p>Some coverage of this report has gone further than the evidence, describing it as an attempt to share all API data. The report itself does not support that version. The reporter explicitly states that private paths, unrelated logs, account identifiers, and credentials are excluded from the report, and that the report establishes unwanted integration and instruction changes, not data exfiltration. The remote MCP connection, the only channel that could have carried data to Postman's server, failed at startup because authentication was required, so in this instance it carried nothing.</p>
<p>Two limits apply to everything above. First, this is a single-user account, detailed and log-backed but not yet independently reproduced in the material reviewed, so it proves what happened on one machine, not what happens on every machine. Second, Postman's intent is unknown: an automatic upgrade path for existing users could be a bug, a mis-scoped rollout, or a deliberate growth tactic, and the logs alone cannot distinguish those. What the logs do settle is the mechanism. The installation was automatic, it crossed into two unrelated tools, and it happened without a prompt the user can point to.</p>
<h2>Why this is a trust-boundary problem, not just a bug</h2>
<p>Coding agents run with a developer's credentials, source code access, cloud tokens, and often production deployment permissions. A plugin inside such an agent is not a theme or a toolbar button. It is code that runs where the developer's secrets live, and a trusted hook can change what the agent does before the developer sees it. That is why the plugin installation path has become a security frontier in its own right: a September 2026 disclosure, widely discussed as Plugin4Shell, showed that the install mechanism shared by major coding agents could run code without further interaction, and the fix was to treat installed plugins as software supply chain, with allowlists and provenance checks.</p>
<p>Postman's case lands awkwardly against its own recent work. On September 15, 2026, Postman announced general availability of Passport, a product that keeps real API credentials inside the customer's environment while developers and agents receive governed, task-scoped access. The idea behind Passport is that agents should act without holding the keys. The desktop behavior reported here points the other way: an agent's configuration changed without the developer's governed approval, which is exactly the failure Passport exists to prevent. Readers do not need to resolve whether this was a bug or a strategy to see the contradiction. A vendor cannot sell governed agent access with one hand and auto-install into agents with the other and expect developers to trust either gesture.</p>
<p>For developers, the practical response is an audit, not a boycott. Check the plugin sections of your coding agent configurations for entries you did not add, check the installed-plugins record for timestamps that match application launches rather than your own actions, check your local binary folder for executables you did not place there, and disable automatic plugin installation where your agent supports it, requiring an explicit, logged action instead. That routine is also the durable lesson of this story, and it connects directly to the question ByteHerald examined in <a href="https://www.byteherald.com/2026/10/ai-agents-need-id-agent-identity-stack.html">our comparison of the emerging agent identity stack</a>: who verifies an agent, what credential it carries, and who is liable when it acts. A plugin installed without asking is an identity the developer never issued. And it belongs beside <a href="https://www.byteherald.com/2026/10/the-great-agent-lockout-who-blocks-ai.html">our map of who blocks AI agents, and what it costs</a>, because blocking and silent installation are the two sides of the same unresolved question: who gets to decide what runs inside an agent.</p>
