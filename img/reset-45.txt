By ByteHerald's arithmetic, 57.61 GiB of resident memory leaves about 5.2 GiB of headroom against a 62.8 GiB usable figure for a 64 GB Linux machine as stated on the model card. The fit is therefore a quantization and sparsity result, not a dense-model result: most parameters sit in routed experts that do not all fire per token.</p><h2>What remains unproven</h2><p>Analysis: the ledger proves capacity, not quality. The independent audit states its author could not run the model on a virtual machine with about 6 GB of RAM, so speed figures remain the project author's measurements checked for consistency. The quality gate reported by the project is the author's own test, and the audit reads it as non-discriminating because the baseline also scored at the ceiling. Until an independent run publishes perplexity or task scores against the unquantized model on named hardware, the honest claim is narrow: a 284B mixture-of-experts checkpoint fits and runs at author-reported CPU speeds inside 64 GB, with answer quality at 1.71 bits per weight still open.</p><p>The runtime requirement is part of the claim, not a footnote to it. The model card states that the checkpoint uses custom tensor type 40 and that unpatched llama.cpp, Ollama, or LM Studio builds fail with an unknown tensor type error, so the 64 GB result depends on the patched llama-modchip engine or its bundled binary. A reader testing the claim therefore needs three things at once: the 56.56 GiB checkpoint, a 64 GB machine, and the matching runtime. Missing any one of the three reproduces a failure that says nothing about the quantization arithmetic.</p><p>Context length belongs in the same test record, because resident memory at 256K context is the figure the model card reports, and a shorter context would understate the memory a long agent session actually holds.</p><p>By ByteHerald Staff.
