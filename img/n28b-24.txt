<p>ByteHerald's incident ledger shows a capacity check that should have been mechanical. Cloudflare advertised a 1,048,576-token context for GLM-5.3 while the prefill key-value pool held 681,280 tokens. The gap was 367,296 tokens, about 35.0 percent of the advertised context. Every one of the 155 affected responses went to a prompt longer than the pool. A startup assertion comparing configured context with actual pool capacity would have caught the mismatch before launch.</p>

<h2>How two faults combined</h2>
<p>The pool mismatch alone should have produced an error for an over-length prompt. The SGLang rejection path turned it into exposure. A rejected request was replaced with a one-token placeholder, yet decode still read the reserved allocation. Pages retained earlier content because key-value pages are reused without clearing for performance. Decode therefore generated from one fresh page and stale pages left by earlier requests, returning HTTP 200 instead of an error.</p>
<p>Analysis: the failure is a boundary-contract failure. Context length, pool capacity, admission state and page ownership are separate values that must agree. Testing only HTTP status at long context missed the correctness condition. A safer launch test sends two accounts with canary strings, submits prompts above pool capacity, and asserts that the second account cannot receive the first account's canary in text, streaming frames or error bodies.</p>
<h2>Response and remaining questions</h2>
<p>Cloudflare said the report arrived at 23:11 UTC on September 8, 2026, the incident was declared the next day, the model was set private at 14:00 UTC, and a corrected configuration raised the pool to about 2.04 million tokens. SGLang fixes moved rejection earlier so a rejected request is retired before allocation or transfer. Cloudflare said no other Workers AI model was affected.</p>
<p>Analysis: operators should add three checks after this incident. First, fail startup when advertised context exceeds measured pool capacity. Second, treat rejected as terminal in every scheduler state, including disaggregated handoff. Third, run cross-tenant canary tests whenever cache paging, prefix reuse or disaggregation changes. Those checks are cheap beside the cost of a tenant-isolation failure.</p>
<p>Analysis: the disclosure timeline is part of the technical record. Cloudflare fixed the serving configuration on September 9, 2026, while public disclosure waited until October 26, 2026 after upstream fixes shipped. That sequence can be reasonable when a bug affects an open-source engine used by others. It also means customers operated for weeks without a public explanation of a tenant-isolation failure. Operators should therefore track engine advisories and version changes, not only provider status pages. A model can be restored quickly while the underlying admission bug remains relevant to every deployment on the older engine version.</p><p>The version record matters because the same admission state can exist outside Cloudflare wherever disaggregated serving is used.</p><p>Analysis: a complete operator response should include a regression test in continuous integration. The test can use a small pool, a prompt above capacity, and two tenants with distinct canary strings. It should assert a client error or a clean single-tenant answer, never a mixed answer. The test should also inspect streaming output, because a correct final status can hide leaked frames.
